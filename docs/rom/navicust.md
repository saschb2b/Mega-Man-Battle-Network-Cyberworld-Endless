| NaviCust (`src/layer/navicust.c`, [The NaviCust](../game/navicust.md)) | `0x13B22C` program records; RAM `0x0200431C` bug counts; key item `0x71` ExpMemry | Program records, 16 bytes per colour variant (program x 4 + variant): +0 category, +1 program part 0 / plus part 1 / either 2, +3 colour (1 White, 2 Yellow, 3 Pink, 4 Red, 5 Blue, 6 Green; 0 absent), +4 bug type, +8 and +0xC the shape and compressed shape: pointers to 49 bytes, seven rows of seven cells, nonzero where a block stands (SuprArmr 7 blocks, one over two rows of three; Custom1 6; HP+50 2 in a column; `navicust_shape`). The boards at `0x13CFCC`, `0x13D0AD` and `0x13D18E` are 15x15 maps of the 4x4, 5x4 and 5x5 boards (1 a cell, 3 the frame); the command line is their third row. Checked against the NaviCust screen: SuprArmr and Custom1 cannot share the 4x4 board without a bug (a playtester's, and `navicust_pack`), and share the 5x4. Found through the literal pool at `0x13D56C` in Gregar's NaviCust code (Falzar's `StructArr_813944C`, the block shifted by 0x1DE0); verified by SuprArmr's variant 4 reading Red and Attack+1's variants 140-142 Pink, Red, Blue, and by the program a draft gives showing in that colour on the NaviCust screen. The bug counts are one byte per type (eToolkit +0x60, Gregar's toolkit offset table at `0x6CC8`); a part left hanging past the board's edge counted an HP bug there while RUN still said OK. `F4 00 71 01` gives an ExpMemry and the game regrows the board: the act 2 guardian's showed a 5x4 board afterwards. |
| NaviCust compression (`src/layer/navicust.c` navicust_shape_as, `src/director/director_board.c` shape_now and codes_bring, issue #54) | event flags `BN6_FLAG_COMPRESSED` (`0x2660`) + variant; Gregar `0x0813D580` the shape lookup (bn6f sub_813B7A0), its flag literal at `0x0813D5C8` | A program record's +8 points at its shape, +0xC at its compressed one (Custom1 6 blocks to 4, SuperArmor 7 to 4, UnderSht's program 7 to 5; plus parts the same). The shape lookup tests flag 0x2660 + the variant and reads +0xC where it is set, else +8; entering a program's compression code on the NaviCust screen (the toggle after its tenth button, Gregar's literal at `0x0813E180`) sets or clears the flags of all four of its colour variants at once, 0x2660 + program x 4 on, so entered again it undoes itself. A run starts from a fresh game, its flags clear; codes_bring sets them as a run begins for the programs whose code the profile knows ([The meta layer](../game/meta/overview.md)). Every compressed shape is a subset of its full one, cell for cell: the 64 colour variants whose +0xC points into the ROM, read from the records (`0x13B22C`, 16 bytes a variant) and compared over their 7x7 grids. Found in bn6f's NaviCust code (`sub_813B7A0`, the code input's `SetEventFlagRange`), and the same bytes in Gregar (`d0b5 0e1c 041c ... 0822 0e49`, the literal 0x2660). MegaMan's fit checks read the shapes so (the draft, made with the layer before a CONTINUE's state is back, keeps the uncompressed ones). Verify: with Custom1 in the PET, `play.py` dev step `flags 9832 9835 1` (0x2668-0x266B; the step reaches every flag of eEventFlags' 1448 bytes, `BN6_EVENT_FLAG_BYTES`, bn6f's ewram.s) draws it in its four-block shape on the NaviCust screen; with it placed and SuperArmor's flags 0x2664-0x2667 set too, MegaMan says SuperArmor needs a program moved, where uncompressed it would not fit the 4x4 board at all. |

| NaviCust's board (`src/director/director_board.c` program_off_board) | RAM `0x02004190` the placed programs; key items `0x90` + program x 4 + variant | A program MegaMan has is a key item, `0x90` + program x 4 + its colour variant (bn6f `sub_803D148`, which `GiveNaviCustPrograms` calls), and its count stays when it is placed. The board's programs are a list at `0x02004190`, 8 bytes each: +0 u16 program x 4 + variant, +3 column, +4 row, +5 turns (0-3); a 0 ends it. Found by comparing a playtester's saved states: before a session UnderSht's key item `0xC4` was 1 and the list empty; after placing it, SuperArmor and HP+100 the list held `0x04` (turned 180, turns 2), `0x34` at column 5 and `0xAA`, as his notes describe, with the key items unchanged. The board itself is RAM `0x0200414C` (eToolkit +0x58 in Falzar's `sub_813B9B4`), a 7x7 grid, a byte a cell: the placed program's index in the list + 1, 0 none. BN6's compile (bn6f `sub_813BBD4`) lands a shape's 7x7 pattern at its column and row less 3, reads the command line as the grid's row 3, counts a bug for a part of record kind 1 (a plus part) there, and sees colours touch only inside the grid's inner 5x5 (the mask at `sub_813C624`). The 4x4 board stands at x 1-4, y 1-4 of it, the 5-wide at x 1-5. Found by printing it in a replay of a playtester's session: his pink HP+100 (variant `0xA9`, column 2, row 3) filled x 2-3, y 2-3, and the NaviCust screen showed it in the board's second and third columns and rows, over the command line, with a light HP bug counted. `navicust_bug_cause` names the rule from it. |
